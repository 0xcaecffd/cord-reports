This is one connected story in three acts. First, a pair of critical PHP flaws that early reporting called hard to exploit, which our lab showed to be exploitable on default installations. Second, the malware attackers pushed through that hole within hours of disclosure, which we caught in the wild. Third, the crew behind it: their tools, their infrastructure, and a money trail on the blockchain that runs back to named exchanges.

The full indicator list is in the appendix and in iocs.csv. We name no individuals. Attribution is to a group, defined by its code, its infrastructure and its wallets.

Patch now. PHP 8.3.36 and later fix CVE-2026-109618 and CVE-2026-109619. If you run PHP with sessions enabled and cannot patch today, see Detect the exploitation.

Act I: the exploit (PHP2Shell)#

What the flaw is#

CVE-2026-109618 and CVE-2026-109619 are use-after-free bugs in PHP's session upload-progress handling. When a request runs out of memory while PHP is still parsing it, PHP abandons the request without the normal clean-up and leaves stale pointers in its memory allocator. A follow-up request to the same worker then reads that corrupted memory before any application code runs. Both were patched in PHP 8.3.36 while already being exploited in the wild.

Why "hard to exploit" was wrong#

Early public reporting said exploitation needed an unusually low memory limit (memory_limit=8M). Our lab reproduction showed that is not true. A stock installation with the default 128 MB limit can be driven out of memory by a request of a few hundred kilobytes, well inside the default upload size, because of how PHP builds its internal upload metadata. The attack traffic looks like ordinary form data, not a large or unusual payload.

Results from default Docker images:

Build Result
PHP 8.3.35 (vulnerable) Worker crashes in 14 of 15 test rounds, with the crash inside PHP's allocator
PHP 8.3.36 (patched) 0 crashes in 261 runs of identical traffic

Follow-on lab work turned the crash into working remote code execution as the web server user on unpatched builds, with unauthenticated HTTP access only. We are not publishing the exploitation details.

During the same work we identified a further, separate PHP session issue. It is in coordinated disclosure and is not described here.

What this means for defenders#

  • Treat any PHP 8.x below 8.3.36 that uses sessions as remotely exploitable, whatever its memory settings.
  • Detection that looks for an oversized upload misses this attack. Look for the behaviour instead (see What to do).

Act II: the payload we caught in the wild#

Within hours of the patch, attackers were using this flaw to plant a second-stage bot. We obtained the sample. It turned out to be far more than a run-of-the-mill Mirai copy (Mirai being the widely copied botnet code that most Linux DDoS malware descends from).

What it is. A Linux DDoS bot: software that turns a compromised server into a foot soldier for knocking other sites offline. It does not spread on its own. It is placed onto servers through the PHP2Shell exploit. It is the newest build of a family that Nokia Deepfield documented in May 2026 under the name potassium, and the same binary the research firm ELLIO identified on 2026-10-22 as the PHP2Shell second stage, seen in the wild the day before.

Why it stands out. Ordinary Mirai copies leave their settings and tell-tale text in plain sight. This one encrypts everything: a 476-slot string table locked under ChaCha20, with even the cipher's own constant masked. Its link back to the operators uses modern cryptography (X25519 key exchange, ChaCha20-Poly1305). It can open a remote shell, hide its own process and update itself. It lies about where its control server is (see Act III). And the scanner classic Mirai uses to spread on its own has been removed: this build is placed deliberately by a loader rather than spreading like a worm.

The wider family and our confidence#

This sample is one build off a production line. We scored every related file in the CORD corpus and ran four detection rules back across a year of global malware submissions. Ranked by how sure we are:

  • Same operator, high confidence. Two x86-64 sibling builds, 6f272c85365a… (2026-10-04) and b58cf55ad3e6… (2026-09-23), carry the same encrypted blockchain settings and overlapping control-server lists once decrypted. This sample and 6f272c85365a… share two control-server hosts outright. Both build lines registered their blockchain names through the same service and point at the same operator-specific resolver.
  • Same operator, likely. Six ARM builds from September and October 2026. One of them (5420b2745e8d…) was seen reaching the same control server as our sample.
  • Same toolkit, operator unproven. Three un-stripped "developer" builds that shipped with their source-file names intact, plus two older ARM builds.
  • Fresh finds (2026-10-22). Our retrohunt surfaced 23 more in-the-wild builds: six x86-64 and seventeen ARM, SuperH and x86, including versions bundled inside Android app packages. Our four rules flagged all of them with no false alarms on clean software.

This is an actively maintained, multi-platform family, from Linux servers to Android devices.

Act III: the operator#

The crew is careful, but careful people are consistent, and consistency makes a pattern.

Their infrastructure#

They rotate their control-server domains on a schedule: a new .st domain every few weeks (with one two-month gap over the summer), bought through two small resellers, each dressed up with a legitimate-looking web page, with the real control servers on short subdomains. Their hosting spans Estonia, France, Switzerland, Russia, Armenia and DigitalOcean. New infrastructure typically goes live about a week before a new build ships.

The sleight of hand: decoy DNS#

When the bot looks up its control domain, it never connects to the address it gets back. It scrambles that address first. Older builds swap the two halves. This build keeps the first number and rotates the rest. The addresses anyone can see in DNS point at university, military and ordinary consumer networks: innocent bystanders. Blocking the published address does nothing, and would hurt the wrong people. We reversed the scramble and recovered the real servers, including the live one at 134.199.154[.]64 (DigitalOcean), plus eight more behind the group's other hosts.

A C2 fallback on the blockchain#

The configuration holds a backup plan. If the domains are ever taken down, the bot can look up its control-server address on the Ethereum blockchain instead, a public ledger that no registrar or hosting provider can switch off. It reads a text record labelled ip from three ENS names: 2sexy4u[.]eth and sushiconsumer[.]eth (this sample) and catswithhatslolksjhakf[.]eth (the siblings), through the public ENS registry and one operator-specific resolver (0xf29100983e058b709f3d539b0c765937b804ac15). This build does not use it yet: the feature is built but not switched on. The values parked there appear to be scrambled with the same decoy trick. Unwinding three of the October values with this build's scramble lands them in the same DigitalOcean range as the live server.

Following the money#

Because the blockchain is public, we could read who owns those names and who paid for them. This is the strongest thread in the investigation.

  • Two wallets, one playbook. The sample's two names sit in one wallet (0x32ab9ef9…da7b). The siblings' name sits in a second (0xd5e34876…f995). Both registered through the same service and point at the same resolver: an on-chain tie between the two build lines, on top of the control-server hosts they share in code.
  • The second wallet is a smart contract, an account-abstraction setup that keeps the controlling key off the public ledger. It has been active since 2025, so it was held in reserve rather than created for this campaign.
  • Both wallets were funded through throwaway relay wallets, used once and discarded to break the trail. No mixer was used. The one anonymity step is a single no-KYC swap (ChangeNOW) on one branch, so the trail is bent, not cut.
  • Both branches reach exchanges that know their customers. The relay that seeded the smart-contract wallet was funded on 2025-06-10 by a Coinbase hot wallet (0xb5d85cbf…). Coinbase verifies its account holders, so that withdrawal ties to an account the exchange can identify under legal process.
  • The other branch runs through a busy shared cash-movement service. Money enters it from a KuCoin wallet (0x45300136…) and leaves to a Binance deposit address (0x16f59CEf…), with one detour through ChangeNOW (0x3f3Ee0a9…). Because the service moves money for many unrelated people, KuCoin and Binance here are leads to confirm, not proof.

Every branch ends either at an exchange that keeps customer records or at the no-KYC swap. Naming anyone from here means legal process at those exchanges. Attribution stays with the operator group.

What their tradecraft tells us#

They are competent and deliberate: encrypted builds, rotating infrastructure, decoy addressing, disposable funding wallets, a blockchain fallback waiting in the wings, and wallet keys kept off the public record. The discipline is uneven, though. Developer builds slipped out with their internal file names, and the money trail touches a named exchange. Two soft signals, held loosely, point toward a European operator: their blockchain activity clusters between 06:00 and 14:00 UTC, and Deepfield observed Dutch-language content in an earlier campaign.

What to do about it#

Detect the exploitation#

  • Upgrade to PHP 8.3.36 or later.
  • Alert on bursts of multipart/form-data POSTs carrying PHP_SESSION_UPLOAD_PROGRESS to pages that do not accept uploads.
  • Alert on PHP workers that run out of memory and crash (SIGSEGV) in bursts.
  • Alert on any web-server worker that starts a shell and then downloads a file.

Detect the malware#

Four YARA rules cover the family across architectures with no hits on clean software (16,686 ELF samples, 4,699 Linux system binaries and 1,542 Windows files tested):

Rule Scope
elf_mirai_ext_x64_build_family x86-64 builds from this code generator (tight)
elf_mirai_ext_x64_chacha_lineage x86-64 builds with the lineage's ChaCha20 routine
elf_mirai_ext_multiarch_literals Any architecture, by literal-pool constants
elf_masked_chacha_constant_survey Wide survey rule for triage

All four in one file: potassium-all.yar.

Block and hunt the infrastructure#

  • Block the real, recovered control servers in the appendix, never the published DNS answers, which belong to bystanders.
  • On Linux hosts, look for a loopback listener on TCP port 1234, a hidden directory at /var/tmp/.cache/sysd, files at /tmp/.manta or /tmp/.xwiki, and a process whose /proc entry is masked by another.
  • Watch the three ENS names for record changes (a read-only query), watch for new .st domains from the same two resellers, and pivot on the relay wallets.
